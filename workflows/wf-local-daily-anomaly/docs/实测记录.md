> 补充：两者对「调用技能」的写法一致（均为 `anomaly-detect`），此处无冲突；冲突在**步骤命名**与**触发方式**。

### 6.3 技能文档的可执行性缺陷
1. **`anomaly_detect.py` 只评估序列末点，抓不到中段异常**：`detect()` 仅用 `values[-1]` 与 `values[-2]` 判定，
   本次 W34（第 8 期）脏数据在 12 期全序列下**命中 0 条**，必须人工把序列截到 W34 才暴露。`SKILL.md` 未说明该局限。
2. **「环比 −100.0%」措辞有误导风险**：`mom = (3.1 − 49800)/49800` 直接取整为「跌 100.0%」，容易被读成「归零/关店」；
   而实际问题只是单位错误。脚本未输出「疑似单位错误」提示，`SKILL.md` 也未要求在明显数量级异常时先排查单位。
3. **员工契约与技能归属自相矛盾**：`employee.yaml` 把 `anomaly-detect` 登记为 `kind: private`（本仓私有），
   但 `skills/anomaly-detect/SKILL.md` frontmatter 写 `library: agent-skills-library`、归属 `PLATFORM`、可见性 `platform_shared`。同一技能两处归属相反。
4. **工作流级 SKILL.md 的「步骤↔技能」是事后推导**：`SKILL.md` 自述「步骤与关联技能的对应是指示性映射（依注册表 `calls` 顺序推导）」——
   即步骤名并非来自真实编排，才导致与 `WORKFLOW.md` 命名漂移（见 6.2）。
5. **步骤 1 的「输入来源」模板空转**：`WORKFLOW.md` 两处步骤的输入来源均写「上一步产出 / 本员工知识库 / 连接器只读数据」，
   第一步无「上一步」，模板占位未替换。
